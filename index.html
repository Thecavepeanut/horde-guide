PREPARED FOR THE GUILD

Horde Field Guide to Claude Code

From first install to a live personal page, for any Horde player. Any class, any starting skill level.

Welcome. This is a wiki, so skip around. Each page covers one thing, the sidebar groups them, and the search box finds any word. Tick the quest box at the bottom of a page when you have done it. Your progress stays in your browser, so a closed tab will not wipe it.

You will finish with Claude Code running on your machine, a clear picture of how context, memory, models and effort work, and a personal page that reads its content from a GitHub Gist. Think of it as a character sheet for the web: who you are, what you play, a few links. That page is your hello world.

How the guide is laid out
Base Camp gets you installed and through a first session. The Road covers context, handoffs as flight paths, and memory as hearths and summons. The Toolbox covers models, effort and the extension features. The Quest builds the personal page. Raiding is three raids: Onyxia for review, Molten Core for polish and Naxxramas for retros. Every page is a zone, from Durotar to Naxxramas, so the guide reads like a leveling route. Side Quests and Reference are for later, once you have the loot from the first four.

The route

BASE CAMP

Durotar: Gear Up

Every orc and troll starts in Durotar with a hearth, a quest list and a few supplies. Yours are below.

You need five things before the first pull: Node.js, Git, a code editor, a GitHub account, and a Claude plan that includes Claude Code. Everything here is free except the plan.

  1. Node.js LTS
    Go to nodejs.org and click the LTS button. Run the installer with the defaults. Claude Code's npm package needs Node 22 or newer, and the current LTS meets that.
  2. Git for Windows
    Go to git-scm.com and install with the defaults. This gives you Git Bash, a terminal that behaves the same as on Mac and Linux. Claude Code can run without it on Windows, but the Bash tool works better with it.
  3. VS Code
    Go to code.visualstudio.com. Tick every box on the "Additional Tasks" screen, especially Add to PATH, so you can type code . in any folder.
  4. GitHub account and the GitHub CLI
    Make a free account at github.com. Then install the CLI from cli.github.com. It is called gh, and the personal page project uses it to create your gist.
  5. A Claude plan
    Claude Code needs Pro, Max, Ultra, Team, Enterprise or a Console account. The free claude.ai plan does not include it. Sign up at claude.ai.

Open a new Git Bash window and check each tool.

VERIFY EVERYTHING
node --version      # v22 or higher
npm --version
git --version
gh --version
Mac or Linux
The same tools apply. Use Homebrew if you have it (brew install node gh git), and use the Terminal app wherever this guide says Git Bash.

BASE CAMP

The Barrens: Install Claude Code

On this page

The Barrens is long and flat and has one main road. The install is the same: pick a route and follow it. Barrens chat is not included.

Two routes work. Because you are already installing Node, the npm route keeps everything in one toolbox, so it is the main path here. The native installer is what Anthropic recommends and it updates itself, so it is a fine alternative.

Route A: npm (matches the rest of this guide)

GIT BASH OR POWERSHELL
npm install -g @anthropic-ai/claude-code@latest

Never put sudo in front of that command on Mac or Linux. If npm complains about permissions, fix your npm prefix or use route B. To update later, run the same command again.

Route B: native installer (no Node needed for Claude Code itself)

POWERSHELL (NO ADMIN NEEDED)
irm https://claude.ai/install.ps1 | iex

Winget also works: winget install Anthropic.ClaudeCode.

Log in and check

ANY TERMINAL
claude --version
claude doctor
claude

claude doctor prints a read-only health report. Running plain claude opens a browser tab so you can sign in with the account that has your plan. If claude is "not found", close the terminal and open a new one so it picks up the new PATH.

Run it from a project folder
Claude Code works on whatever folder you start it in, so always cd into the project first. Never start it in your Downloads folder or your home directory.

BASE CAMP

Stranglethorn Vale: Your First Pull

On this page

Stranglethorn Vale is where hunters go to learn the job. Your first real session works the same way: pick a target, pull, and see what comes back.

A session is a loop. You describe a goal, Claude reads files and proposes changes, you approve or redirect, and it carries on. Claude attacks whatever you point it at, so aim before you pull.

START A PRACTICE PROJECT
mkdir hello-claude
cd hello-claude
git init
claude

Try these prompts in order. Each one shows a different habit.

  1. Look around
    Ask: "What is in this folder, and what could we build here?" Claude reads before it acts.
  2. Make something small
    Ask: "Create a single HTML page that says hello, in the style of a Horde quest log." You will see Claude ask permission before writing a file.
  3. Change it
    Ask: "Make the title bigger and add today's date." Claude edits the file in place.
  4. Undo
    Press Esc twice with an empty prompt to open the rewind menu. You can roll back the conversation, the code, or both. It is the closest thing to a respawn you will get.

Permission modes

Press Shift+Tab to cycle modes. Manual asks before each edit. Accept edits lets file changes through while still asking about commands. Plan mode lets Claude read and think but change nothing. Type /plan to jump straight into plan mode.

Use plan mode first on anything big
Ask for a plan, read it, fix the parts you disagree with, then let Claude build. A bad plan is cheap to change. A bad build costs context and time, and you cannot wipe and retry for free.

Handy habits

  • Mention files with @, for example "look at @page.json".
  • Give Claude a way to check its work: "run the page and tell me if the console shows errors".
  • One task per session. When the task is done, start fresh.

THE ROAD

Orgrimmar: Your Bags

On this page

Your bags hold a fixed number of slots, and Claude's context window works the same way. Everything in the conversation takes up room: your messages, Claude's replies, every file it reads, every command output. When the window fills, older detail gets squeezed out or summarized and quality drops.

What eats context

  • Files Claude reads, especially large ones
  • Long command output such as test logs and build logs
  • Web pages and search results
  • Instruction files and connected tools, which load at the start of every session
  • Long back-and-forth when you change direction repeatedly

Commands for managing it

CommandWhat it does
/contextShows how full the window is as a colored grid. Add all for more detail, including what your memory files and connected tools cost.
/compactSummarizes the conversation to free space. Add instructions to steer it, for example /compact keep the decisions and the file list.
/clearStarts a new conversation with empty context. Give it a name to label the old one.
/resumeReturns to an earlier conversation, by name or from a picker.
/rewindRolls the code and the conversation back to a checkpoint. Esc twice does the same.

Habits that save bag space

  • Start a new session for each task. Finishing a feature and starting an unrelated one in the same thread wastes space.
  • Ask for exploration through a subagent when the answer needs a lot of reading. The subagent reads the files in its own window and sends back a short summary.
  • Put stable rules in CLAUDE.md once instead of repeating them in chat.
  • Paste only the part of a log that matters.

The Crossroads: Handoffs as Flight Paths

On this page

The Crossroads is the flight path hub of the Barrens. A handoff is a flight path: you note where you are going and what you carry, and the next session lands at the other end without walking the whole zone again.

These are working rules of thumb, and the exact limits move around. Quality tends to slip well before the window is completely full, so reset on a schedule and skip the wait for trouble.

Context usedWhat to do
Around 100k tokensStart planning your exit. Find the nearest flight master. Finish the step you are on, stop starting new threads, and decide what the next session needs to know.
Around 200k tokensReset now. Take the flight. Write the handoff, then /clear or open a new session. Do not push on.

Run /context to see where you are. If you use a 1M-context model, the habit still holds. A longer window gives you room, and a focused session still works better than a bloated one.

Write your flight path

A handoff is a short note that lets a fresh session pick up where this one stopped. Ask Claude to write it before you reset.

PROMPT TO USE AT THE END OF A SESSION
Write HANDOFF.md for the next session. Include:
1. Goal and current status in two sentences
2. What is done and what is left, as a checklist
3. Decisions we made and why
4. Files that matter, with one line each
5. Commands to run and the last result
6. Open problems and my next prompt
Keep it under 60 lines. Facts only.
PROMPT TO START THE NEXT SESSION
Read HANDOFF.md and @CLAUDE.md, tell me the plan in three lines,
then wait for my go-ahead.

Flight path versus compact

A compact is a quick heal: use /compact when you want to keep going in the same conversation and the thread is still healthy. Use a handoff plus /clear when the task is changing, the thread has wandered, or you passed the 200k line. The handoff file survives anything, including a closed laptop, so it also works across days.

Keep it out of Git
List HANDOFF.md in your .gitignore. Handoffs are working notes and have no place in the project history.

Undercity: Hearths and Summons (Memory)

On this page

Every session starts blank, like a fresh login. Two things carry knowledge across sessions: your hearthstone, which is the instructions you write in CLAUDE.md, and summons, which are the notes Claude writes about you. Together they are your memory system.

Your hearthstone: CLAUDE.md

A hearthstone returns you to the same place every time, and CLAUDE.md does that for every session. Claude reads these files at the start of each session. They load in layers, from broad to specific, and combine instead of overriding each other.

WhereScope
~/.claude/CLAUDE.mdYou, in every project. Your background, tone and habits.
./CLAUDE.md or ./.claude/CLAUDE.mdThis project, shared through Git. Commands, conventions, rules.
./CLAUDE.local.mdYour private notes for this project. Add it to .gitignore.

Run /init inside a project and Claude drafts a CLAUDE.md from what it finds. If one exists, it suggests improvements instead of overwriting. Run /memory to open any of these files, and to see what is loaded.

What belongs in it

Build commands, how to run tests, folder layout, naming rules, things Claude must never do, and your preferences. Keep each file under about 200 lines. Longer files use more context and get followed less closely.

A STARTER ~/.claude/CLAUDE.md
# About me
I play a Horde class and I am new to programming. Use plain
language, and game comparisons when they help. Show me the
command before running it.

# How to work with me
- Plan first on anything touching more than two files.
- Never invent facts, names, numbers or dates. Ask me instead.
- Ask before you publish or push anything.
- Prefer plain Node.js with no dependencies.

Summons: auto memory

A summon pulls the right thing to you without a long walk. Auto memory works like that: Claude writes the notes itself and brings them back when they matter. It is on by default. When you correct Claude or state a preference, it can save a note on its own. The notes live under ~/.claude/projects/<project>/memory/, with a MEMORY.md index that loads at the start of each session. You can ask directly: "remember that I use Git Bash on Windows". Turn it off in /memory or with CLAUDE_CODE_DISABLE_AUTO_MEMORY=1.

Hearths are advice, and Claude can still miss one

Claude treats these files as context. It follows them well and still misses one now and then. For a rule that must never break, such as "never run this command", use a hook or a permission rule, covered on the Toolbox pages.

Check what is loaded
If Claude ignores a rule, run /context all and look under Memory files. A rule in the wrong folder never loads.

Gadgetzan: Models and Effort

On this page

The goblins of Gadgetzan will sell you anything, so the skill is picking the right tool for the job.

Pick the cheapest setup that does the job well. You would not spend a raid cooldown on a single mob. Two dials matter: which model, and how hard it thinks.

The models

AliasUse it for
haikuQuick, mechanical work: renaming, formatting, simple edits, summarizing a file. Fastest and cheapest.
sonnetDaily coding: building features, fixing bugs, refactors, most of your personal page.
opusHard reasoning: architecture, tricky bugs, reviewing a whole project, deciding between designs.
opusplanOpus while in plan mode, then Sonnet to carry out the plan. A good default for big tasks.
fableThe hardest and longest-running work, when the docs say your plan offers it.

Add [1m] for a 1M-context variant, for example opus[1m]. On the Anthropic API, opus, sonnet and haiku currently point at Opus 5.5, Sonnet 5.5 and Haiku 5.5.

Switching

MODEL COMMANDS
/model              # open the picker
/model sonnet       # switch and save as your default
claude --model haiku

In the picker, Enter saves your choice as the default and s changes only the current session.

Effort: how long it thinks

Effort sets how much reasoning Claude spends before answering. The levels are low, medium, high, xhigh and max. Set it with /effort high, or /effort auto to clear it. The docs list medium as the default for the 5.5 models. max lasts for the current session only.

LevelWhen
lowTypos, renames, "what does this line do"
mediumNormal building and editing
highBugs you cannot explain, changes touching several files
xhigh or maxDesign decisions, security review, anything where a wrong answer is expensive

Matching tool to job

JobModel and effort
Fix a typo in page.jsonhaiku, low
Add a new section to your pagesonnet, medium
Debug why the gist will not loadsonnet, high
Plan a bigger project, such as a raid schedule pageopusplan or opus, high
Review the finished page before you share itopus, high or xhigh

Higher effort and bigger models spend your plan's usage faster. Run /usage to see where you stand. When a cheaper setup stalls twice, move up one step instead of re-asking the same thing.

Models for helpers

Subagents have their own model setting, so a research helper can run on haiku while your main session runs on sonnet. See the next page.

Un'Goro Crater: Skills, Subagents, Hooks, MCP, Plugins

On this page

Claude Code has five ways to extend it. Each solves a different problem, and knowing which to reach for saves a lot of trial and error.

FeatureUse it when
CLAUDE.mdYou want a rule or fact loaded in every session
SkillYou have a repeatable workflow or reference Claude should load only when relevant
SubagentA task needs its own context window, or should run in parallel, and returns a summary
HookSomething must happen automatically on every matching event, with no exceptions
MCPClaude needs to reach an outside service such as GitHub, a database or a calendar
PluginYou want to package skills, hooks, subagents and MCP servers so you can reuse or share them

Skills

A skill is a folder with a SKILL.md file. Claude loads its short description at the start and the full text only when the task matches, or when you type /skill-name. Personal skills live in ~/.claude/skills/<name>/, project skills in .claude/skills/<name>/.

.claude/skills/check-page/SKILL.md
---
description: Proofread page.json and look for private info before I publish
disable-model-invocation: true
---
Read page.json. List typos and unclear sentences with a suggested fix
for each. Then scan every field for a phone number, a home address, an
email I did not mean to share, or a real full name. Report what you
find and change nothing. Ask me before editing.

With disable-model-invocation: true, the skill runs only when you type it. That suits any workflow you want to trigger yourself, and it is the right setting for anything that publishes.

Subagents

A subagent is a helper with its own context window. It does the reading and sends back a summary, which saves room in your bags. Define one as a markdown file in .claude/agents/ or ~/.claude/agents/, or just ask: "use a subagent to find every place the site reads the gist URL".

.claude/agents/reviewer.md
---
name: reviewer
description: Reviews changes for mistakes before I commit
tools: Read, Glob, Grep
model: sonnet
---
Review the current changes. Report real problems only, with file
and line. Do not edit anything.

Hooks

A hook runs a script or command on an event, such as before a tool runs or after a file is edited. Claude does not decide whether to run it. That makes hooks the right place for rules that must hold, like blocking edits to a protected file.

MCP

MCP servers connect Claude to outside services. Manage them with /mcp. They cost context, because their tool names load at the start. Check the cost with /context all. Install only the ones you use, prefer read-only access, and check who made each server before you connect it.

Plugins

A plugin bundles several of the above into one installable unit. Open /plugin to browse. Plugin skills are namespaced, for example /my-plugin:review.

TOOLBOX

Silithus: Artifacts

On this page

An artifact is a live web page that Claude publishes from your session to a private link on claude.ai. This guide you are reading is one. You ask in plain language and Claude writes the page, publishes it, and prints the link.

How to use them

  • Ask: "make an artifact that explains my personal page project as a diagram".
  • To change one, ask Claude to revise it. It republishes to the same link.
  • /artifacts lists yours. Ctrl+] reopens the latest one.
  • Sharing is controlled from the page header. On Pro and Max the only option is a public link that anyone can open, so keep personal data off pages you share.

Limits to know

  • Needs a Pro, Max, Ultra, Team or Enterprise plan and a session signed in with /login. An API key alone cannot publish.
  • The page source is HTML or Markdown, under 16 MiB, and it has no backend.
  • A page cannot start downloads or open the print dialog, so artifacts suit reading and interacting, and a PDF suits printing.

Artifact, gist or GitHub Pages

ToolBest for
ArtifactA polished page you want Claude to build and revise, shared by link
GistA single file or small set of text files, with history, that code and sites can read
GitHub PagesA permanent website at your own address, built from a repository

Your personal page project uses all three ideas together: the gist holds the data, Pages serves the site, and an artifact is a quick way to prototype a design before you commit to it.

THE QUEST

Thunder Bluff: Your Personal Page

On this page

Thunder Bluff is a home built on top of a mesa. Your personal page is your home on the web.

Your hello world is a character sheet for the web: a page about you, what you play, a few projects or links, and a way to reach you. It reads its content from a GitHub Gist. It touches nearly everything in this guide: a real project folder, a CLAUDE.md, plan mode, a connected service, a deploy, and a loop for updating it.

How it fits together

THE FLOW
page.json  --publish-->  GitHub Gist  --fetch-->  your website
(on your PC)             (the data)                (GitHub Pages)

You edit page.json. One command copies it to a gist. The website downloads the gist when someone opens the page and draws it. Edit the gist and the site updates in a few minutes, with no redeploy.

Why a gist works here

Raw gist URLs allow browsers on other sites to fetch them, so a static page can load the data directly. They cache for about five minutes. A gist also keeps a revision history of every edit, so a bad change is easy to undo.

What Claude will build

You start from an empty folder. The prompt on the next page asks Claude for this layout.

FileJob
page.jsonYour content as data: name or handle, tagline, about, what you play, projects and links, contact.
docs/The website: index.html, style.css and app.js, plus config.js with your gist URL.
bin/page.mjsThree commands: check, serve and publish. Plain Node, no dependencies.
CLAUDE.mdProject memory, including a rule to never publish without asking.
.gitignoreKeeps HANDOFF.md and private files out of Git.

Public or secret

A public gist is listed on your GitHub profile and anyone can find it. A secret gist is unlisted, and anyone with the link can still read it. Either way the site shows its content to the whole internet, so write page.json as if a stranger will read it.

Privacy note
Leave out your phone number, your home address and your real name unless you want them public. A handle, a Discord tag you are happy to share, or a link to a profile you already use is plenty for the contact section.

Mulgore: Build It Step by Step

Work through these in order. Every prompt is meant to be pasted into Claude Code from inside the project folder. Start with the first prompt, which makes Claude build the whole project from scratch.

PASTE THIS FIRST, IN PLAN MODE
Build a personal "character sheet" website in this empty folder.
Node 22 only, no dependencies. Requirements:
1. page.json holds all content: name or handle, tagline, about me,
   what I play, a few projects or links, and a contact line
2. docs/ has index.html, style.css and app.js. app.js fetches the
   data from a gist raw URL stored in docs/config.js, falls back to
   a local copy of page.json, and renders everything with
   textContent only, never innerHTML
3. bin/page.mjs with check, serve and publish commands. check tests
   Node, gh login and that page.json parses. serve hosts docs/ on
   localhost:3000. publish uses gh api to create or update a gist,
   saves its id in page.config.json, points docs/config.js at it,
   and supports --dry-run
4. a CLAUDE.md that says never to publish or push without asking
5. a .gitignore that lists HANDOFF.md and CLAUDE.local.md
Plan first and wait for my approval before writing files.
  1. Open the folder
    Make an empty folder such as my-page somewhere like Documents, cd into it, run git init, then claude. Paste the prompt above in plan mode (Shift+Tab, or /plan). Read the plan, ask for changes, then approve it. Afterward ask: "Read CLAUDE.md and explain how this project works in five lines."
  2. Log in to GitHub
    Run gh auth login and follow the browser prompts. Then run node bin/page.mjs check. Every line should say ok.
  3. Preview the site
    Run node bin/page.mjs serve and open http://localhost:3000. You should see your page. Press Ctrl+C to stop it.
  4. Make it yours
    Back in plan mode, ask: "Plan the changes needed so page.json says what I want. Ask me questions first. Never invent a fact." Answer honestly, approve the plan, and let Claude edit page.json.
  5. Dry run the publish
    Run node bin/page.mjs publish --dry-run. It prints what it would do and sends nothing. Check the visibility line.
  6. Publish the gist
    Run node bin/page.mjs publish. It creates the gist, saves its id in page.config.json, and points docs/config.js at it.
  7. Put it on GitHub Pages
    Ask Claude: "Create a GitHub repository for this folder, commit everything, and push. Ask me before the push." Then in the repository go to Settings, Pages, and deploy from branch main, folder /docs. Your site appears at https://<your-username>.github.io/<repo-name>/.
  8. Update later
    Edit page.json, run node bin/page.mjs publish, commit if you changed the site files. The gist updates in place, so the link never changes.
Why the dry run exists
Publishing creates something on the internet under your name. Always look at what is about to happen first. The CLAUDE.md from the prompt tells Claude to ask before publishing, and that habit belongs in every project you make.

Stretch goals

  • Add a "Party" section that links to your guildmates' pages.
  • Add a print-friendly layout so the page saves as a clean PDF from your browser.
  • Add a dark and light toggle that remembers your choice.
  • Add a screenshot gallery that reads image links from page.json.

RAIDING

Raid 1: Onyxia's Layer by Layer

This is the endgame habit set. A raid group does not just pull and hope. It checks the plan, fixes mistakes and reads the logs afterward. Claude is fast, and it is also confident when it is wrong. Three habits turn it from a quick pull into a reliable raid partner: have it review the work, clean up the writing, and look back at what went wrong after every run.

Onyxia's Lair is the first big test, and it is a code review in disguise. She hits in three phases, and her Deep Breath punishes anyone standing in the wrong spot. Unreviewed code works the same way. It looks fine until it lands on everything at once. Peel it back one layer at a time before you commit or publish.

ToolUse it for
/code-reviewReviews your current changes, or a pull request, for real bugs. Pass an effort level first, for example /code-review high. Low is quick and shallow, high and above dig deeper and cost more.
/simplifyLooks at what you changed for repeated code and needless complexity, then applies the fixes.
/security-reviewA security pass over the pending changes on your branch. Run it before you publish anything.
A reviewer subagentThe helper from the Skills page. It reads in its own window and reports only real problems.
A GOOD REVIEW PROMPT
Review everything we changed this session. List real problems only,
with file and line. Check that nothing private (names, emails, keys)
ended up in a file that gets published. Do not edit anything yet.

A short, clean review does not prove the code is clean, especially at low effort. For anything you plan to share, use a higher effort level, or run the review on a stronger model than the one that wrote the code.

RAIDING

Raid 2: Molten Core, Melt the Filler

Text from a model has habits, and people notice them: the same sentence shapes, filler openers, long dashes everywhere, contrasts like "not X, but Y". Ragnaros does not leave until you have ground through the whole core, and the stock phrases are the same. Bring fire resistance and melt them out before you publish. A humanizer skill is a set of rules for finding and removing those habits so your page, your posts and your messages sound like you.

  • Search /plugin for a humanizer or writing-cleanup skill, or write your own. A skill is just a markdown file of rules.
  • Run it on anything public: your personal page text, a guild post, a pull request description.
  • Give it a sample of your own writing so it matches your voice.
  • It should never add facts. Read the result and make sure it still says only what is true.

RAIDING

Raid 3: Naxxramas, the Post-Mortem Necropolis

Naxxramas is the endgame raid for a reason. It has four wings, and every wipe teaches you something. Kel'Thuzad waits at the end for any group that skipped the logs. The most useful skill you can write is a post-mortem, and a necropolis is the right place for one. After a piece of work, it looks back at the session, finds what went wrong or took too long, and writes down what to change. Over time those notes become a ledger of which skills and habits help and which waste your time.

.claude/skills/retro/SKILL.md
---
description: Post-mortem after a task. Find issues and suggest fixes
disable-model-invocation: true
---
Look back over this session. Write at most three entries to
~/.claude/retros/log.md, newest first. For each one give:
- what we were doing
- what went wrong, got slow, or surprised us, and why it matters
- one concrete suggestion (a CLAUDE.md rule, a skill change, a hook)
Verdict each entry GOOD (worked, keep), BAD (wasted effort, change it)
or UGLY (new, not judged yet). Be specific. Skip the run if nothing
was worth noting.

Run /retro at the end of a task, before you write a handoff. Every few weeks read the log, promote repeat problems into CLAUDE.md rules or hooks, and delete skills that keep landing in BAD. This is how a setup improves instead of piling up.

Make it a habit
Build, review, polish, retro, handoff. Five steps, and the last three take a few minutes. The retro is the one that pays you back on the next task.

The Hinterlands: Side Quests

On this page

Once the personal page is live, the same pattern works for anything a guild wants to track: a JSON file in a gist, a static page that draws it, and one command to update it. Use invented sample data while you build, and swap in real data only if everyone it names agrees to share it.

QuestWhat it is
Guild roster pageA table of members with class, role and main or alt status, filterable by role. Start with ten made-up characters.
Raid schedule pageRaid nights, start times in local time, and who signed up, read from one file the officers edit.
Loot council or DKP trackerA points ledger with a history of awards and spends, and a check that balances never go negative. Invented names and numbers only.
Farming route or profession cost calculatorPick a recipe, see the materials, and add up the cost from prices you type in. A good first use of plan mode.
Reminder page without a Discord botA page that counts down to the next raid or reset and can be bookmarked or pinned to a phone home screen.
Addon idea listA page that collects addon ideas with a short spec each, so a guildmate who writes addons can pick one up.

How to start any of them

A FIRST PROMPT FOR ANY SIDE QUEST
I want to build <project> for my guild. Use only invented sample
data. Plan first: ask me what the page should answer at a glance,
propose a file layout and a first milestone I can finish in an
evening, then wait for my approval.

Each side quest gets its own folder, its own CLAUDE.md, and its own gist. Start with one screen and one data file, and add features after the first version works.

Use Claude for everyday stuff

  • Spreadsheets: ask it to build a budget, a gold tracker, or a formula for a column you cannot crack.
  • Planning: ask it to turn a messy week of work, school and raid nights into a schedule you can follow.
  • Learning: ask it to explain a topic at your level, then quiz you until the answers stick.

Barrens Chat: When Things Go Wrong

Barrens chat is famous for bad advice and worse jokes. This page is the useful kind.

ProblemTry this
claude: command not foundClose and reopen the terminal. If it persists, run claude doctor, then reinstall using route B.
npm permission errorsDo not use sudo. Use the native installer or fix the npm global folder.
Login loop or wrong accountRun /login and sign in with the account that has the plan.
gh: command not foundInstall the GitHub CLI from cli.github.com and open a new terminal.
node bin/page.mjs check fails on loginRun gh auth login and choose the browser option.
Site shows old contentRaw gists cache for about five minutes. Wait, then hard refresh.
Page blank on GitHub PagesConfirm Pages points at the /docs folder and that docs/config.js holds your gist URL.
Claude forgets your rulesRun /context all and check the memory files are listed. Keep CLAUDE.md under about 200 lines.
Answers get worse late in a long sessionCheck /context. Write a handoff and reset.
You are burning through your usageDrop to sonnet and medium effort for routine work. Save opus for planning.
Claude edited something you did not wantPress Esc twice and rewind, or use git restore on the file.

Ask your guildmates. Or ask Claude itself: paste the exact error and say what you were doing. Include the command and the full message, and skip the summary.
